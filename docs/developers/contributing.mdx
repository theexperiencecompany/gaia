Bug fixes, features, docs and tests are all welcome. AI-assisted pull requests are fine: just say so.

For a large change, open an [issue](https://github.com/theexperiencecompany/gaia/issues) or [discussion](https://github.com/theexperiencecompany/gaia/discussions) first, so we agree on the approach.

<Steps>
  <Step title="Fork and clone">
    Fork the repository on GitHub, then clone your fork and add the original as `upstream`:

    ```bash
    git clone https://github.com/YOUR_USERNAME/gaia.git
    cd gaia
    git remote add upstream https://github.com/theexperiencecompany/gaia.git
    ```

    Then follow [Set up for development](/developers/development-setup) from step 2.
  </Step>

  <Step title="Create a branch from master">
    `master` is the only long-lived branch.

    ```bash
    git checkout -b fix/chat-draft-lost
    ```
  </Step>

  <Step title="Make the change, with a test">
    Follow the `CLAUDE.md` in the folder you change (see [Project tour](/developers/project-tour#rules-that-live-next-to-the-code)). New behavior ships with a test. A bug fix ships with a test that fails without the fix. See [Testing](/developers/testing).
  </Step>

  <Step title="Run the checks">
    ```bash
    mise run lint         # TypeScript and the Nx projects
    mise run lint:py      # all Python
    mise run type-check
    ```

    Add the tests for what you changed. `mise run lint:fix` and `mise run lint:py:fix` fix most lint findings.
  </Step>

  <Step title="Commit">
    Use a [conventional commit](/configuration/conventional-commits) message.

    ```bash
    git add <files>
    git commit -m "fix(web): keep the draft when switching chats"
    ```

    With the hooks installed (`mise run pre-commit:install`), commits run the linters, and pushes run the CI checks your change affects. That can take a few minutes.
  </Step>

  <Step title="Merge master if it moved">
    Use a merge, not a rebase:

    ```bash
    git fetch upstream
    git merge upstream/master
    ```
  </Step>

  <Step title="Push and open the pull request">
    ```bash
    git push origin fix/chat-draft-lost
    ```

    Open the pull request against `master`. Its title uses the same format as a commit, and CI rejects any other. See the [allowed types](/configuration/conventional-commits#supported-types).
  </Step>

  <Step title="Fill in the template">
    Write the description for someone who has never seen your branch. Delete sections that don't apply.

    - **Summary** and **Why**: what changes for the user, and why.
    - **What changed**, grouped by area.
    - **The bug**, for fixes: root cause and how the fix addresses it.
    - **Screenshots** for anything visual.
    - **How to verify**: steps a reviewer can follow.
  </Step>
</Steps>

## What happens next

1. CI runs on every push. Open a failed check to read its log.
2. A maintainer reviews and may comment.
3. Push more commits to the same branch to answer. The pull request updates itself.
4. A maintainer merges it once it's approved and green.

Contributors are credited in the README, and in the release notes for significant changes.

## Common problems

<AccordionGroup>
  <Accordion title="A CI check failed">
    Read the log. Most failures name the file and line. The table in the [repository's CLAUDE.md](https://github.com/theexperiencecompany/gaia/blob/master/CLAUDE.md#verify-with-the-ci-command-not-a-lookalike) maps each kind of change to its command. Run it locally, fix, commit and push.
  </Accordion>

  <Accordion title="The pull request has merge conflicts">
    Merge `master` into your branch, resolve the conflicts git reports, then commit and push.
  </Accordion>

  <Accordion title="The title check failed">
    Edit the title so it starts with an allowed type, like `fix:` or `feat(web):`. The check reruns on its own.
  </Accordion>
</AccordionGroup>

Need help? Ask in [Discord](https://discord.heygaia.io), [GitHub Discussions](https://github.com/theexperiencecompany/gaia/discussions) or on the issue.
