Bug fixes, features, docs and tests are all welcome. So are pull requests written with AI tools such as Claude or Cursor: just say so in the description.

For a large change, open an [issue](https://github.com/theexperiencecompany/gaia/issues) or a [discussion](https://github.com/theexperiencecompany/gaia/discussions) first, so we can agree on the approach before you build it.

## The workflow

<Steps>
  <Step title="Fork and clone">
    Fork the repository on GitHub, then clone your fork and add the original as a second remote named `upstream`:

    ```bash
    git clone https://github.com/YOUR_USERNAME/gaia.git
    cd gaia
    git remote add upstream https://github.com/theexperiencecompany/gaia.git
    ```

    Then follow [Set up GAIA for development](/developers/development-setup) from step 2.
  </Step>

  <Step title="Create a branch from master">
    `master` is the only long-lived branch. Name yours after the change, for example:

    ```bash
    git checkout -b fix/chat-draft-lost
    ```
  </Step>

  <Step title="Make the change, with a test">
    Follow the rules in the `CLAUDE.md` of the folder you are changing (see [Project tour](/developers/project-tour#rules-that-live-next-to-the-code)). New behavior ships with a test. A bug fix ships with a test that fails without the fix. [Testing](/developers/testing) explains which kind.
  </Step>

  <Step title="Run the checks">
    ```bash
    mise run lint         # TypeScript and the Nx projects
    mise run lint:py      # all Python
    mise run type-check
    ```

    Plus the tests for what you changed, from [Testing](/developers/testing). `mise run lint:fix` and `mise run lint:py:fix` fix most lint findings for you.
  </Step>

  <Step title="Commit">
    Use a [conventional commit](/configuration/conventional-commits) message: a type, an optional scope, and a short summary.

    ```bash
    git add <files>
    git commit -m "fix(web): keep the draft when switching chats"
    ```

    If you installed the hooks (`mise run pre-commit:install`), each commit runs the formatters and linters on the staged files, and each push first runs, locally, the CI checks your change affects. That can take a few minutes.
  </Step>

  <Step title="Stay up to date with master">
    If `master` moved while you worked, merge it into your branch. Use a merge, not a rebase:

    ```bash
    git fetch upstream
    git merge upstream/master
    ```
  </Step>

  <Step title="Push and open the pull request">
    ```bash
    git push origin fix/chat-draft-lost
    ```

    Open the pull request against `master`. Its **title** uses the same conventional format as a commit, for example `fix(web): keep the draft when switching chats`. A CI check rejects any other format. The allowed types are listed in [Commit messages](/configuration/conventional-commits#supported-types).
  </Step>

  <Step title="Fill in the template">
    The description opens with a template (`.github/pull_request_template.md`). Write it for someone who has never seen your branch:

    - **Summary** and **Why**: what changes for the user, and the reason.
    - **What changed**, grouped by area (API, Web, Bots / Mobile, Infra).
    - **The bug**, for fixes: what happened, the root cause and how the fix addresses it.
    - **Screenshots** for anything visual.
    - **How to verify**: the steps a reviewer follows to see it work.

    Delete the sections that don't apply instead of writing "none".
  </Step>
</Steps>

## Review

1. **CI runs** on every push: lint, types, tests and a set of quality checks. Each check appears at the bottom of the pull request. Open a failed one to read its log.
2. **A maintainer reviews** your code and may leave comments.
3. **You push more commits** to the same branch to answer them. The pull request updates on its own.
4. **A maintainer merges** it once it's approved and green.

After the merge you can delete your branch. Contributors are credited in the README's contributors section, and in the release notes for significant changes.

## Common problems

<AccordionGroup>
  <Accordion title="A CI check failed">
    Open the check and read its log. Most failures name the file and line. Run the same command locally (the table in the [repository's CLAUDE.md](https://github.com/theexperiencecompany/gaia/blob/master/CLAUDE.md#verify-with-the-ci-command-not-a-lookalike) maps each kind of change to its command), fix it, commit and push.
  </Accordion>

  <Accordion title="The pull request has merge conflicts">
    Merge `master` into your branch as in step 6, resolve the conflicts git reports, then commit and push.
  </Accordion>

  <Accordion title="The title check failed">
    Edit the pull request title so it starts with an allowed type, for example `fix:` or `feat(web):`. The check runs again on its own.
  </Accordion>
</AccordionGroup>
