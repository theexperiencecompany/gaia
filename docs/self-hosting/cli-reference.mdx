## Overview

These are the `gaia` commands for running your own GAIA: setup, running, logs, health checks, backups and shutdown. The contributor commands (`gaia init`, `gaia setup`, `gaia dev`) are in the [developer CLI commands](/developers/cli-internals#the-developer-commands-optional).

```bash
gaia up            # Install and start GAIA (self-host), or resume a half-finished install
gaia update        # Move to the GAIA release this CLI ships (self-host)
gaia status        # Services and every dependency, with latency
gaia doctor        # Diagnose a GAIA install, with a fix per problem
gaia backup        # Dump the databases, volumes and apps/api/.env
gaia restore       # Restore that backup
gaia start         # Start self-host services
gaia stop          # Stop services
gaia logs          # Stream logs
gaia --version     # Show CLI version
gaia --help        # Show all commands
```

| Command          | Description                                                                  |
| ---------------- | ---------------------------------------------------------------------------- |
| `gaia up`        | One-command setup: configure, pull and start GAIA (self-host)                |
| `gaia update`    | Move to the release this CLI ships: pin its images, pull them and restart    |
| `gaia backup`    | Dump MongoDB, PostgreSQL, the storage volumes and `apps/api/.env` to `./backups` |
| `gaia restore`   | Restore a backup, `apps/api/.env` (the credential key) first, then restart  |
| `gaia start`     | Start GAIA services in self-host mode                                        |
| `gaia logs`      | Stream logs for currently running services                                   |
| `gaia stop`      | Stop running GAIA services                                                   |
| `gaia status`    | Check health and latency of GAIA services and their dependencies             |
| `gaia doctor`    | Diagnose a GAIA install: docker, services and setup checks                   |
| `gaia uninstall` | Remove GAIA from this computer; asks before deleting your data               |
| `gaia --version` | Display the current CLI version                                              |
| `gaia --help`    | Show help and available commands                                             |

<Note>
  `gaia bridge` connects a machine to GAIA over a secure outbound tunnel so the
  agent can run commands on it and read or write its files, and reach its local
  MCP servers. It has its own commands and setup — see the
  [Device Bridge](/cli/device-bridge) guide. On macOS and Linux you can also
  connect the computer you're on with one click from the GAIA desktop app, no
  CLI required.
</Note>

## `gaia up`

One-command setup: configure, pull and start GAIA (self-host).

```bash
gaia up
```

Combines configuration, image pull/build and startup into a single command. It needs Docker, not Git: on a fresh machine it downloads this release's setup files (`gaia-selfhost-<version>.tar.gz` from the `cli-v<version>` GitHub Release), checks them against their `.sha256` and unpacks them into `~/gaia`. GAIA is served on one port through a bundled proxy: the web app at `/` and the API at `/api/v1`.

**Options:**

| Flag                     | Description                                                        |
| ------------------------ | ------------------------------------------------------------------ |
| `--yes`                  | Install Docker without asking when it is missing (apt-based Linux), and Git too for `--build` on a fresh machine. Nothing else in `gaia up` asks a question |
| `--llm-provider <name>`  | AI provider to save once GAIA is up, as the setup wizard would: `openrouter`, `gemini`, `openai`, `ollama` or `custom` |
| `--llm-key <key>`        | API key for `--llm-provider`. Required for `openrouter`, `gemini`, `openai` and `custom`; refused for `ollama` |
| `--llm-base-url <url>`   | Endpoint for `ollama` (optional, default `http://host.docker.internal:11434`) or `custom` (required) |
| `--llm-model <model>`    | Model for `ollama` (optional) or `custom` (required) |
| `--web-port <port>`      | Host port GAIA is served on (default 3000)                         |
| `--domain <domain>`      | Serve GAIA at `https://<domain>` with an automatic certificate (uses ports 80 and 443) |
| `-b, --build`            | Build images from source before starting. Needs a source checkout: on a fresh machine it clones the source; on a bundle install it refuses and points at `gaia init` |
| `--code-sandbox`         | Run agent code in local containers through the host Docker socket (root-equivalent; saved for later starts and updates) — see [Local coding sandbox](/self-hosting/docker-setup#local-coding-sandbox) |
| `--no-code-sandbox`      | Turn the local code sandbox off again                              |
| `--no-start`             | Configure environment only; do not start services. Refused with `--llm-provider` |
| `--no-local-name`        | Don't name GAIA `http://gaia.local` on your network. A run with it also removes a name an earlier run set up |
| `--force-dev-tree`       | Allow operating on a developer checkout that is not the install    |

```bash
# Fully non-interactive first boot
gaia up --yes --llm-provider openai --llm-key <key>

# A local Ollama, no key
gaia up --yes --llm-provider ollama --llm-model qwen3

# Any OpenAI-compatible gateway
gaia up --llm-provider custom --llm-key <key> --llm-base-url https://gateway.example.com/v1 --llm-model <model>

# Public server with HTTPS (DNS must already point at this host)
gaia up --yes --domain gaia.example.com
```

On Linux, if your user cannot reach the Docker socket, `gaia up` adds it to the `docker` group and relaunches itself under `sg docker`, so the same command runs to completion.

### gaia.local on your network

Without `--domain`, `gaia up` also names GAIA `http://gaia.local`, so phones and other computers on the same home or office network open it by name instead of by IP address. It uses [portless](https://github.com/vercel-labs/portless): it installs `portless` with npm (it needs Node.js 24 or newer) and, on Linux, `avahi-utils`; it installs portless's proxy as a startup service in LAN mode, on plain HTTP port 80, so other devices see no certificate warning; and it points `gaia.local` at GAIA's port. The service runs as root, so `gaia up` asks for your sudo password the first time.

If the name can't be set up (port 80 is taken, avahi isn't running, Node.js is too old), `gaia up` still finishes and says why in one line on its summary. With `--domain` there is no `gaia.local`: Caddy needs port 80 for the domain. `--no-local-name` turns it off.

### A local domain with HTTPS

`--domain` with a name no public certificate authority can certify (`.test`, `.internal`, `.home.arpa`, `.local`, `.localhost`, `.example`, `.invalid`) gets its certificate from Caddy's own local authority instead of Let's Encrypt. Devices warn about it until they trust that authority's root, which `gaia up` names on its summary:

```bash
docker cp gaia-selfhost-proxy-1:/data/caddy/pki/authorities/local/root.crt gaia-root.crt
```

Each device must also resolve the name to the server, for example with a line in its `/etc/hosts` or a record on your router's DNS.

## `gaia start`

Start GAIA services in **self-host mode**.

```bash
gaia start
```

**Options:**

| Flag      | Description                             |
| --------- | --------------------------------------- |
| `--build` | Rebuild Docker images before starting   |
| `--pull`  | Pull the images again before starting   |

```bash
gaia start --build --pull
```

<Note>
  In developer mode, use [`gaia dev`](/developers/cli-internals#the-developer-commands-optional) instead of `gaia start`.
</Note>

## `gaia logs`

Stream logs for currently running services.

```bash
gaia logs
```

- Self-host mode: streams Docker service logs.
- Developer mode: streams Docker logs and, when available, app logs.

## `gaia stop`

Stop running GAIA services.

```bash
gaia stop
```

**Options:**

| Flag            | Description                                                                  |
| --------------- | ---------------------------------------------------------------------------- |
| `--force-ports` | Aggressively stop listeners on API/Web ports (may affect non-GAIA processes) |

```bash
gaia stop --force-ports
```

By default, `gaia stop` runs in safe mode and only targets GAIA-managed processes.

## `gaia status`

Check health and latency of GAIA services and of every backing service the API depends on.

```bash
gaia status
```

Besides the web app, the API and the containers, it calls the API's `GET /health/ready` and lists each dependency (MongoDB, PostgreSQL, Redis, RabbitMQ, ChromaDB) with whether it answered, its latency, the error type when it did not, and the command to inspect it.

## `gaia doctor`

Diagnose a GAIA installation: docker, services and setup checks.

```bash
gaia doctor
```

Runs ordered checks against your installation and prints one `[ok]`/`[FAIL]`
line per check with a remediation hint (`Fix: …`) on failure:

1. **Docker daemon** — reachable via `docker info`
2. **Ports** — the ports the stack publishes are free or already GAIA's
3. **Compose containers** — expected services per setup mode
   (`gaia-selfhost` or `gaia-dev`) are running
4. **API health** — `/api/v1/ping` answers (honors `infra/docker/.env` port overrides)
5. **Dependencies** — one line per backing service from `GET /health/ready`,
   with latency, error type and a fix naming the service to inspect
6. **Setup readiness** — plans seeded, LLM provider configured, admin account
   created (and billing, outside self-host); each unconfigured item is a
   warning pointing at the web setup wizard
7. **Web** — reachable on its host port
8. **Disk headroom** — ≥ 2 GB free on the Docker data root
9. **Memory headroom** — warns under 4 GB available, fails under 2 GB
10. **GAIA version** — warns when the pinned images are not the release this
    CLI ships, pointing at `gaia update`

Checks that depend on an earlier failure are skipped instead of failing again.

**Exit code:** `1` only when a *blocking* check fails. Setup-readiness
warnings never affect the exit code, so `gaia doctor` is safe to run in
scripts and CI.

Output is plain text in every environment (TTY or not), so reports can be
piped or pasted directly into bug reports:

```bash
$ gaia doctor

gaia doctor
  [ok]  Docker daemon
  [FAIL] Compose containers (gaia-selfhost) — gaia-web missing
         Fix: Run 'gaia start' to bring the stack up, or check 'docker compose -p gaia-selfhost logs'.
  [ok]  API health (http://localhost:3000/api/v1) — HTTP 200
  [ok]  Dependency: mongodb — 1.4ms
  [FAIL] Dependency: rabbitmq — TimeoutError after 2001ms
         Fix: Check its logs: docker compose -p gaia-selfhost logs rabbitmq (it takes up to a minute to boot after a restart, so rerun first).
  ...

Summary: 2 blocking.
```

## Port Conflict Handling

If required ports are in use, the CLI:

1. Detects the conflicting process
2. Suggests alternative ports
3. Writes overrides to `infra/docker/.env`

Overrides persist across restarts and are reused by `gaia start`, `gaia logs`, and `gaia status`.

## Upgrading

### Updating GAIA

```bash
gaia update                 # add --yes to skip the confirmation
gaia update --version v0.7.0  # move to another release: its images and its cli-v0.7.0 setup files
gaia update --git           # contributors: pull your branch and rebuild from source
```

Every CLI release ships one tested GAIA release. `gaia update` moves your install to it: it downloads that release's setup files and checks them against their `.sha256`, pulls its images (so a failed download or pull changes nothing), swaps the setup files in and removes any the release dropped, pins `GAIA_VERSION=v<version>` in `infra/docker/.env`, and restarts. It prints the old and new version, never deletes volumes, and keeps your `.env` files and `backups/`.

An install made by an older `gaia up` is a git checkout of a release tag. Its next `gaia update` moves it to the bundle layout: the tracked files and `.git` are removed, and settings and backups stay. A checkout on a branch, or one with local edits, is refused and pointed at `gaia update --git`.

To get a newer GAIA, update the CLI first (below), then run `gaia update`.

### Updating the CLI

<CodeGroup>

```bash npm
npm install -g @heygaia/cli
```

```bash pnpm
pnpm add -g @heygaia/cli
```

```bash bun
bun add -g @heygaia/cli
```

</CodeGroup>

## `gaia uninstall`

Remove GAIA from this computer.

```bash
gaia uninstall
```

It asks before it removes anything, then whether to delete your data too (accounts, chats, memories and files; the answer defaults to no), and before deleting it offers a backup to `~/gaia-backups` with `gaia backup`. It then removes GAIA's containers, networks and images (`docker compose down --rmi all`, plus `--volumes` when the data goes), the `gaia.local` name and its portless service, the install folder and `~/.gaia`.

Kept data stays in its Docker volumes, and the install folder keeps `apps/api/.env` and `infra/docker/.env`, the settings that unlock it. A later `gaia up` picks both back up. The summary prints the command that deletes them later.

**Options:**

| Flag            | Description                                                             |
| --------------- | ----------------------------------------------------------------------- |
| `--yes`         | Don't ask: uninstall and keep the data, with no backup                  |
| `--delete-data` | Delete the data too (can't be undone). With `--yes`, nothing asks first |

It removes only the install `gaia up` recorded, and refuses a development copy of GAIA.

Last, remove the CLI itself:

<CodeGroup>

```bash npm
npm uninstall -g @heygaia/cli
```

```bash pnpm
pnpm remove -g @heygaia/cli
```

```bash bun
bun remove -g @heygaia/cli
```

</CodeGroup>
