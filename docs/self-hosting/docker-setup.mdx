GAIA uses Docker Compose to orchestrate all the required services. This makes deployment simple and ensures consistency across different environments.

<Note>
  **Looking for the easy path?** [GAIA CLI](/self-hosting/cli-setup) does all of this for you — `gaia up` checks prerequisites, writes configuration, and starts the same Compose stack described here. This guide covers driving Docker directly for advanced users who prefer full control.
</Note>

## Prerequisites

Before you follow the steps below on a fresh machine (e.g. an Ubuntu VM), confirm you have:

- **Docker** — Docker Desktop (macOS/Windows), Docker Engine 20.10+ with Compose v2 (Linux), or OrbStack (macOS). `gaia up` will offer to install Docker if it is missing — see [Docker Installation](#prerequisites-1) below.
- **Git** — only if you use the `git clone` alternative in step 1 (`sudo apt-get install -y git` on Ubuntu/Debian).
- **8 GB RAM minimum** — plus 2+ CPU cores and 10 GB free disk. The local embedding model loads ~1.8 GB into each of `gaia-backend` and `arq_worker` on first use (see [Memory sizing](#memory-sizing)).
- **Ports** — only `3000` must be free on the host (override with `WEB_HOST_PORT`); with a domain, `80` and `443` instead (see [HTTPS on your own domain](#https-on-your-own-domain)). The API and every datastore stay on the internal Docker network and are never published to the host.
- **No API keys to boot** — the stack starts with no provider keys. Add one later at `http://localhost:3000/setup` (or replace `localhost` with your server's IP/hostname), or run entirely keyless against a local Ollama at `http://host.docker.internal:11434`.
- **No manual `.env` setup, no Infisical** — `gaia up` writes `apps/api/.env` (`ENV=selfhost`, `AUTH_MODE=local`) and generates the three machine secrets (`AGENT_SECRET`, `BOT_SESSION_TOKEN_SECRET`, `EMAIL_UNSUBSCRIBE_SECRET`) for you. Never `cp .env.example .env` and self-host never contacts Infisical.

## Self-Host vs Cloud

Same codebase, different operating profile. Self-host runs with `ENV=selfhost` and `AUTH_MODE=local`; Cloud and development use `AUTH_MODE=workos`.

| Area | Cloud (heygaia.io) | Self-Host (`ENV=selfhost`) |
| --- | --- | --- |
| **Auth** | WorkOS / AuthKit — Google OAuth, hosted sessions | Local email + password, single admin account, `AUTH_MODE=local` |
| **Billing** | Dodo Payments — plans and limits enforced | No billing integration; Free plan auto-seeds, `billing_enabled=false`, usage tracked locally only |
| **Secrets** | Infisical vault (required in production) | Local `.env` only; never contacts Infisical; `INSTANCE_SECRET` auto-generated into Mongo (`instance_settings`) on first boot |
| **Required config** | Full SaaS keys (OpenRouter, Gemini, Tavily, Composio, R2, LiveKit, etc.) required to boot | Only infra + 3 machine secrets (`MONGO_DB`, `REDIS_URL`, `POSTGRES_URL`, `CHROMADB_*`, `RABBITMQ_URL`, `AGENT_SECRET`, `BOT_SESSION_TOKEN_SECRET`, `EMAIL_UNSUBSCRIBE_SECRET`) — everything else is optional and disables gracefully; providers configured at runtime via the setup wizard |
| **LLM providers** | Managed keys via Infisical | Bring your own — OpenRouter / Gemini / Ollama / OpenCode / Nous via Settings; keys encrypted with the instance secret |
| **Workspace storage** | Hosted R2 + JuiceFS (managed) | Bring your own R2/S3 + Postgres meta DB via `R2_*` / `JUICEFS_META_URL_TEMPLATE`; without it chat works but uploads/artifacts log `JuiceFSUnavailable` |
| **Sandbox** | E2B (required) with warm pool | E2B optional; without it each user's code runs in a local `gaia-sandbox-*` container via the host Docker socket — see [Local coding sandbox](#local-coding-sandbox) |
| **Voice** | Hosted LiveKit + Deepgram + ElevenLabs (required) | Bring your own LiveKit or leave unset to disable voice |
| **Search / scraping** | Tavily, Exa, Firecrawl, SearXNG (keys via Infisical) | Same providers but opt-in via env; unset skips that lane |
| **Email** | Resend (managed) | Optional `RESEND_*` — without it email features stay quiet |
| **Observability** | Loki + Grafana, LogQL over shipped logs | Container `json-file` logs only (10 MB × 3 rotated files); no Loki shipper |
| **Updates** | Deployed by the team | `gaia update` — pulls the latest code and images and restarts; volumes survive |
| **Backups** | Managed | `gaia backup` / `gaia restore` — you own the dumps; see [Backups](#backups) |

## Project Structure

```
gaia/
├── apps/
│   ├── api/
│   │   ├── Dockerfile
│   │   └── .env                # API environment variables
│   └── web/
│       ├── Dockerfile
│       └── ...
├── infra/
│   └── docker/
│       ├── .env                         # Compose settings written by gaia up
│       ├── docker-compose.selfhost.yml  # Self-host stack (pulls images)
│       ├── docker-compose.build.yml     # Override: build images from source
│       └── selfhost/Caddyfile           # Single-origin proxy routes
└── ...
```

The self-host stack is `infra/docker/docker-compose.selfhost.yml`, project name `gaia-selfhost`. Every command below runs from `infra/docker/` and passes `-f docker-compose.selfhost.yml` — Compose only auto-detects the default filename, so without `-f` you'd hit the development compose file instead. Containers have no fixed names, so address them by service name through Compose (`docker compose -f docker-compose.selfhost.yml logs gaia-backend`, not `docker logs gaia-backend`); this also lets a development stack (project `gaia-dev`) run beside a self-hosted one.

The stack is image-only: it pulls the multi-arch (amd64 and arm64) images `ghcr.io/theexperiencecompany/gaia` (API and worker) and `ghcr.io/theexperiencecompany/gaia-web`, all pinned to the same `GAIA_VERSION` tag (default `latest`). Set `GAIA_VERSION` in `infra/docker/.env` to pin a release.

### Building from source

To run your own changes, build the images from your checkout instead of pulling them:

```bash
gaia up --build
# equivalent, from infra/docker/:
docker compose -f docker-compose.selfhost.yml -f docker-compose.build.yml up -d --build
```

The build override keeps the same image tags, so a later plain `up` reuses your local build until the next pull.

<AccordionGroup>
  <Accordion icon="diagram-project" title="Advanced: Architecture">
    **Stack at a glance** — one Compose project, one bridge network, named volumes:

    ```
    browser ──► proxy (WEB_HOST_PORT, default 3000)
                  ├─ /api/v1/* ──► gaia-backend (8000) ──► postgres │ mongo │ redis │ chromadb │ rabbitmq
                  │                     ├─ host.docker.internal ──► Ollama (host, optional)
    ```

    - `proxy` is Caddy, the only service that publishes a host port. `/api/v1/*` — REST, SSE streams and the WebSocket — goes to `gaia-backend`; everything else goes to `gaia-web`.
    - `gaia-web` is the Next.js frontend. The browser calls the same-origin `/api/v1/`, so the stack works on any hostname or IP with no URL configuration; server-side fetches reach the backend directly at `http://gaia-backend:8000`.
    - `gaia-backend` + `arq_worker` are the same image with different `WORKER_TYPE`; both mount the JuiceFS FUSE cache and share `extra_hosts: host.docker.internal:host-gateway` for host services.
    - The API and all datastores are reachable only on the internal network — see [Networking](#networking).

    For the full container spec see `infra/docker/docker-compose.selfhost.yml`.
  </Accordion>
</AccordionGroup>

## Persistent Workspace Storage (JuiceFS and FUSE)

GAIA's per-user workspace (file uploads, agent artifacts, installed skills) is backed by [JuiceFS](https://juicefs.com), a filesystem that stores file **data** in object storage (Cloudflare R2, S3, or any S3-compatible store) and file **metadata** in a database. The backend mounts it at `/mnt/jfs` and reads and writes files there like a local disk.

JuiceFS mounts through **FUSE** (Filesystem in Userspace), a Linux kernel feature. This has direct consequences for where and how you can run the backend.

### Run the backend in a container

Because the mount needs Linux FUSE, run the backend in a container on every platform:

| Host OS | Native (`uvicorn` on the host) | Containerized (Docker) |
| --- | --- | --- |
| Linux | Works if `juicefs` is installed and `/dev/fuse` is accessible | Works |
| macOS | Not supported (no Linux FUSE) | Works, Docker Desktop's Linux VM provides `/dev/fuse` |
| Windows | Not supported (no Linux FUSE) | Works, Docker Desktop / WSL2 provides `/dev/fuse` |

The self-host Compose stack already runs the backend in a container, so all three platforms are covered. The native path is a development-only convenience on Linux.

<Note>
Run the backend in a container even on macOS and Windows. Docker Desktop runs a Linux VM that exposes `/dev/fuse`, so the FUSE mount works inside the container even though the host OS cannot mount it directly.
</Note>

### How the mount works

FUSE lets a userspace program act as a filesystem instead of the kernel:

1. The kernel exposes a device at `/dev/fuse`.
2. The `juicefs mount` process opens that device and attaches itself as the driver for `/mnt/jfs`.
3. When the backend reads or writes a path under `/mnt/jfs`, the kernel routes the call to the JuiceFS process.
4. JuiceFS looks up metadata in its database, fetches or stores the file's chunks in object storage, and serves the result back through `/dev/fuse`.

The backend never sees any of this, it just reads and writes files under `/mnt/jfs`.

### Container settings that make it work

A Docker container is unprivileged by default: it cannot mount filesystems, cannot see host devices, and runs under an AppArmor profile that blocks `mount`. The Compose file grants exactly what FUSE needs and nothing more:

```yaml
gaia-backend:
  environment:
    # Where the backend expects the mount. Must match the mountpoint.
    JUICEFS_HOST_MOUNT_PATH: /mnt/jfs
    # FUSE filesystems can't be watched with inotify, so artifact
    # detection tails the JuiceFS access log instead.
    ARTIFACT_DETECTION_MODE: accesslog
  cap_add:
    - SYS_ADMIN # the mount() syscall requires this capability
  devices:
    - /dev/fuse:/dev/fuse # pass the FUSE device into the container
  security_opt:
    - apparmor:unconfined # lift the default profile that denies mount
  volumes:
    - juicefs_cache:/var/cache/juicefs # keep the local chunk cache warm
```

<AccordionGroup>
  <Accordion icon="key" title="cap_add: SYS_ADMIN">
    The `mount(2)` syscall requires the `CAP_SYS_ADMIN` capability, which Docker drops by default. Without it, `juicefs` cannot perform the mount and fails before it starts. This grants only that one capability, not full `privileged` access.
  </Accordion>
  <Accordion icon="microchip" title="devices: /dev/fuse">
    The JuiceFS process opens `/dev/fuse` to talk to the kernel's FUSE module. Containers see no host devices by default, so this passes the device through. Without it you get `fusermount3: cannot open /dev/fuse: No such file or directory`.
  </Accordion>
  <Accordion icon="shield" title="security_opt: apparmor:unconfined">
    On Ubuntu and Debian hosts, Docker applies a default AppArmor profile that denies the `mount` operation even when the container holds `CAP_SYS_ADMIN`. This lifts that profile. On hosts without AppArmor it has no effect.
  </Accordion>
  <Accordion icon="database" title="volumes: juicefs_cache">
    JuiceFS keeps a local disk cache of file chunks so repeat reads don't go back to object storage. Persisting it in a named volume keeps the cache warm across restarts. This affects speed only, not correctness.
  </Accordion>
</AccordionGroup>

<Warning>
Avoid `privileged: true` as a shortcut. It grants every capability and device to the container, which is a much larger attack surface. The four scoped settings above are the least-privilege way to enable a single FUSE mount.
</Warning>

### Required configuration

The container settings make a mount *possible*. JuiceFS still needs an object store and a metadata database before it will mount. Set these in `apps/api/.env`:

| Variable | Purpose |
| --- | --- |
| `R2_ACCOUNT_ID`, `R2_BUCKET`, `R2_ACCESS_KEY`, `R2_SECRET_KEY` | Cloudflare R2 (or S3-compatible) object store for file data |
| `JUICEFS_META_URL_TEMPLATE` | Connection URL for the metadata database (a PostgreSQL DB works well) |

Until both are configured, the backend starts normally and chat works, but workspace features (uploads, artifacts, skill installs) degrade and log `JuiceFSUnavailable`. See [Environment Variables](/configuration/environment-variables) for the full list.

## Local coding sandbox

Without an E2B key, GAIA runs each user's code in its own local `gaia-sandbox-*` container. To create those containers, `gaia-backend` and `arq_worker` mount the host Docker socket (`/var/run/docker.sock`) and join the socket's group, `DOCKER_SOCKET_GID`, which `gaia up` writes to `infra/docker/.env`.

<Warning>
Access to the Docker socket is equivalent to root on the host: anyone who compromises `gaia-backend` or `arq_worker` controls the machine. To keep sandboxes off your host, save an E2B key. To remove the socket entirely, delete the `/var/run/docker.sock` mount and the `group_add` entry from both services in `docker-compose.selfhost.yml`; coding tools then fail until an E2B key is set.
</Warning>

## Docker Commands

All commands assume you're in `infra/docker/`.

### Starting and Stopping

```bash
# Start all services
docker compose -f docker-compose.selfhost.yml up -d

# Stop all services
docker compose -f docker-compose.selfhost.yml down

# Stop and remove volumes (deletes ALL data)
docker compose -f docker-compose.selfhost.yml down -v
```

Start the stack with the CLI or with `COMPOSE_PROFILES=proxy` set in `infra/docker/.env` (`gaia up` writes it) — without the `proxy` profile no port is published and GAIA is unreachable from the host.

<Tip>
To move to a newer version, run `gaia update`, or by hand: `docker compose -f docker-compose.selfhost.yml pull && docker compose -f docker-compose.selfhost.yml up -d`. Data in volumes survives.
</Tip>

### Viewing Logs

```bash
# View logs for all services
docker compose -f docker-compose.selfhost.yml logs -f

# View logs for specific service
docker compose -f docker-compose.selfhost.yml logs -f gaia-backend

# View logs with timestamps
docker compose -f docker-compose.selfhost.yml logs -f -t

# View last 100 lines
docker compose -f docker-compose.selfhost.yml logs --tail=100 gaia-backend
```

### Service Management

```bash
# Restart a service
docker compose -f docker-compose.selfhost.yml restart gaia-backend

# Rebuild a service from source and restart it
docker compose -f docker-compose.selfhost.yml -f docker-compose.build.yml up -d --build gaia-backend

# Execute commands in running container
docker compose -f docker-compose.selfhost.yml exec gaia-backend bash
docker compose -f docker-compose.selfhost.yml exec postgres psql -U postgres -d langgraph

# Check service status
docker compose -f docker-compose.selfhost.yml ps
```

Services include health checks. Monitor them:

```bash
docker compose -f docker-compose.selfhost.yml ps
```

- `proxy` — Caddy admin endpoint probe
- `gaia-backend` — HTTP health endpoint (`/health`)
- `gaia-web` — HTTP probe on port 3000

- `rabbitmq` — `rabbitmqctl status`

## Networking

Services communicate through the `gaia_network` bridge network:

```bash
# Services reach each other by service name:
# - proxy → gaia-backend:8000 (/api/v1/*), gaia-web:3000 (everything else)
# - gaia-backend → mongo:27017, redis:6379, postgres:5432, chromadb:8000, rabbitmq:5672
# - gaia-web → gaia-backend:8000 (server-side rendering)
```

Only the proxy publishes a port. The API and every datastore are unreachable from the host and the internet. To open a database shell, go through Compose:

```bash
docker compose -f docker-compose.selfhost.yml exec mongo mongosh gaia
docker compose -f docker-compose.selfhost.yml exec postgres psql -U postgres -d langgraph
```

<Warning>
PostgreSQL, MongoDB, Redis, ChromaDB, and RabbitMQ run without authentication by default (RabbitMQ on its well-known `guest`/`guest`), and between them they hold every user, session, provider credential, and the instance secret — an exposed port is remote total data loss. Do not add `ports:` for them to the Compose file.
</Warning>

The backend and worker also get `extra_hosts: host.docker.internal:host-gateway`, which maps `host.docker.internal` to the host machine. This is how containers reach services running directly on your host — most notably a local Ollama at `http://host.docker.internal:11434`.

<Tip>
On Linux hosts, Ollama listens on `127.0.0.1` by default, which the container cannot reach through the gateway. Start it with `OLLAMA_HOST=0.0.0.0 ollama serve`.
</Tip>

The backend trusts `X-Forwarded-For` and `X-Forwarded-Proto`. That is safe because port 8000 is never published — the only peers are containers on `gaia_network` — and Caddy replaces any client-sent forwarding headers with the real client address. Rate limits (login/signup: 10/min per IP) therefore key off the true client IP, and session cookies are marked Secure whenever the browser is on HTTPS.

<Warning>
If you put another proxy in front of Caddy (Cloudflare Tunnel, a load balancer, …), Caddy sees that proxy as the client. Add its address to Caddy's [`trusted_proxies`](https://caddyserver.com/docs/caddyfile/options#trusted-proxies) in `infra/docker/selfhost/Caddyfile`, otherwise every visitor shares one rate-limit bucket.
</Warning>

### HTTPS on your own domain

```bash
gaia up --domain gaia.example.com
```

Caddy obtains and renews a Let's Encrypt certificate for the domain and redirects HTTP to HTTPS. Before running it, point the domain's DNS at the host and make sure ports `80` and `443` are reachable from the internet. `gaia up` sets `HOST` and `FRONTEND_URL` in `apps/api/.env` to `https://gaia.example.com`.

Without the CLI, set `HOST` and `FRONTEND_URL` in `apps/api/.env` to `https://gaia.example.com`, set these in `infra/docker/.env`, and restart the stack:

```bash
GAIA_DOMAIN=gaia.example.com
WEB_HOST_PORT=80
HTTPS_HOST_PORT=443
```

### Using your own reverse proxy

Platforms that bring their own proxy (Coolify, Dokploy, Traefik, …) don't need the bundled one. Leave the `proxy` profile off and route on the shared network:

| Path        | Target              |
| ----------- | ------------------- |
| `/api/v1/*` | `gaia-backend:8000` |
| everything else | `gaia-web:3000` |

Keep SSE responses unbuffered and allow WebSocket upgrades on `/api/v1`. Your proxy must overwrite, not append to, client-sent `X-Forwarded-For`, because the backend trusts it.

## Data Persistence

Data is persisted using Docker volumes (prefixed `gaia-selfhost_`, except `gaia-sandbox-workspace` which is pinned by name):

| Volume                  | Contents              |
| ----------------------- | --------------------- |
| `gaia-selfhost_pgdata`      | PostgreSQL data   |
| `gaia-selfhost_mongo_data`  | MongoDB data      |
| `gaia-selfhost_redis_data`  | Redis data        |
| `gaia-selfhost_chroma_data` | ChromaDB vectors  |
| `gaia-selfhost_rabbitmq_data` | RabbitMQ messages |
| `gaia-selfhost_juicefs_cache` | JuiceFS local chunk cache (speed only, safe to delete) |
| `gaia-selfhost_models_cache` | fastembed ONNX model cache (~1.85 GB, safe to delete — re-downloads) |
| `gaia-sandbox-workspace` | Local sandbox per-user workspace ([local coding sandbox](#local-coding-sandbox); survives recreation) |
| `gaia-selfhost_caddy_data` | Proxy TLS certificates and keys |
| `gaia-selfhost_caddy_config` | Proxy runtime config |

<Warning>
Never reclaim disk space with `docker system prune --volumes` (or `docker volume prune`, or a routine `docker compose down -v`): the `--volumes` flag deletes every named volume above — the entire state of your instance, including users, sessions, provider credentials, and chats. Plain `docker system prune` (no flags) leaves volumes alone; it only removes stopped containers, dangling images, and build cache.
</Warning>

```bash
gaia backup --dry-run                # print the exact docker commands without running them

# Restore — picks the latest dumps in a directory, or pass explicit files:
gaia restore --from backups          # restores mongo-YYYY-MM-DD.gz + postgres-YYYY-MM-DD.sql
gaia restore --mongo backups/mongo-2026-08-27.gz --postgres backups/postgres-2026-08-27.sql
gaia restore --dry-run --from backups # preview restore commands
```

Equivalent one-copy-paste block for manual use (run from `infra/docker/`):

```bash
mkdir -p backups
docker compose -f docker-compose.selfhost.yml exec -T mongo mongodump --archive --gzip > backups/mongo-$(date +%F).gz
docker compose -f docker-compose.selfhost.yml exec -T postgres pg_dump -U postgres -d langgraph > backups/postgres-$(date +%F).sql
```

See the collapsed sections below for consistent-snapshot variants, ChromaDB/RabbitMQ, and restore steps.
</Tip>

Two stores hold data you cannot rebuild:

- **MongoDB** — users, sessions, chats, settings, provider credentials (encrypted at rest), and the [instance secret](#day-2-operations). Lose it and every login and stored provider key is gone with it.
- **PostgreSQL** — agent and conversation state (LangGraph checkpoints).

Redis (queue + cache), ChromaDB (vectors are re-embeddable from source content), RabbitMQ (transient messages), and the JuiceFS workspace (file bytes already live in your object store) are lower-stakes.

<AccordionGroup>
  <Accordion title="Advanced: Manual backup & restore details">
    ### Back up MongoDB

    The database tools ship inside the mongo container. Dump to a gzip archive and redirect it to a file on the host:

    ```bash
    mkdir -p backups
    docker compose -f docker-compose.selfhost.yml exec -T mongo mongodump --archive --gzip > backups/mongo-$(date +%F).gz
    ```

    For a fully consistent snapshot, stop the writers first so nothing changes mid-dump:

    ```bash
    docker compose -f docker-compose.selfhost.yml stop gaia-backend arq_worker
    docker compose -f docker-compose.selfhost.yml exec -T mongo mongodump --archive --gzip > backups/mongo-$(date +%F).gz
    docker compose -f docker-compose.selfhost.yml start gaia-backend arq_worker
    ```

    ### Back up PostgreSQL

    `pg_dump` produces a consistent snapshot on its own — safe against a live stack:

    ```bash
    docker compose -f docker-compose.selfhost.yml exec -T postgres pg_dump -U postgres -d langgraph > backups/postgres-$(date +%F).sql
    ```

    ### Back up ChromaDB

    ChromaDB's vectors are re-embeddable from source content, so this is optional belt-and-braces — it saves you a full re-embedding run after a restore. Stop the writers first so the SQLite store isn't captured mid-write, then tar the data volume from inside the container (GNU tar ships in the image):

    ```bash
    mkdir -p backups
    docker compose -f docker-compose.selfhost.yml stop gaia-backend arq_worker
    docker compose -f docker-compose.selfhost.yml exec chromadb tar czf - -C /chroma/chroma . > backups/chroma-$(date +%F).tar.gz
    docker compose -f docker-compose.selfhost.yml start gaia-backend arq_worker
    ```

    To restore, untar into a fresh volume before starting the stack:

    ```bash
    docker volume create gaia-selfhost_chroma_data
    docker run --rm -v gaia-selfhost_chroma_data:/data -v "$PWD/backups:/backups" alpine \
      tar xzf /backups/chroma-2026-08-24.tar.gz -C /data
    ```

    ### Back up RabbitMQ

    RabbitMQ holds transient messages only — queues and exchanges are re-declared by the backend on boot — so it usually needs no backup. If you've changed topology manually or want queued-job routing preserved across a rebuild, export the broker definitions to stdout:

    ```bash
    mkdir -p backups
    docker compose -f docker-compose.selfhost.yml exec rabbitmq rabbitmqctl export_definitions - > backups/rabbitmq-definitions-$(date +%F).json
    ```

    Definitions capture topology and users (including password hashes) but **not** message contents — queued messages are lost with the volume. Treat an export like a credential file.

    ### Restore MongoDB

    `--drop` replaces existing collections so you don't merge stale and restored state; `-T` disables the pseudo-terminal so the redirected archive reaches `mongorestore`'s stdin:

    ```bash
    docker compose -f docker-compose.selfhost.yml exec -T mongo mongorestore --archive --gzip --drop < backups/mongo-2026-08-24.gz
    ```

    Restart the app containers afterwards so sessions re-issue against the restored data.

    ### Restore PostgreSQL

    Start from an empty schema so the restore doesn't collide with existing tables:

    ```bash
    docker compose -f docker-compose.selfhost.yml exec postgres psql -U postgres -d langgraph -c 'DROP SCHEMA public CASCADE; CREATE SCHEMA public;'
    cat backups/postgres-2026-08-24.sql | docker compose -f docker-compose.selfhost.yml exec -T postgres psql -U postgres -d langgraph
    ```
  </Accordion>
</AccordionGroup>

<Warning>
A Mongo backup decrypts your provider credentials — it contains the instance secret that protects them. Store backups with the same care as `.env` files: off-host, access-controlled, never in a public bucket.
</Warning>

## Day-2 Operations

### Memory sizing

The stack boots in less, but steady-state use is what sets the 8 GB minimum: the local embedding model (fastembed ONNX) loads lazily into **both** `gaia-backend` and `arq_worker` at roughly 1.8 GB resident each — two independent copies, since each process keeps its own singleton — on top of Postgres, MongoDB, Redis, ChromaDB, and RabbitMQ. Plan for a realistic floor of **~8 GB RAM** once memory features are in use; on smaller hosts the failure mode is OOM kills around the first embedding load, not at boot.

### Upgrades

```bash
gaia update
```

It fetches the latest `master` into your checkout, shows what changed, and after you confirm (or with `--yes`) runs `git pull --ff-only` and restarts the services on freshly pulled images, rebuilding locally only when the web image's `Dockerfile` or `package.json` changed. It never runs `down -v` and keeps `infra/docker/.env`. By hand, from `infra/docker/`:

```bash
git pull
docker compose -f docker-compose.selfhost.yml pull
docker compose -f docker-compose.selfhost.yml up -d
```

Named volumes survive the upgrade. After upgrading, watch for vector-index failures: an embedding-model bump makes previously stored vectors stale, and indexing failures are logged (and flagged for later reindexing) rather than taking writes down:

```bash
docker compose -f docker-compose.selfhost.yml logs -f gaia-backend arq_worker | grep -Ei 'index_failed|memory_embedding_failed'
```

### The instance secret

On first boot GAIA generates a root secret and persists it inside MongoDB (the `instance_settings` collection). Everything sensitive derives from it: local session tokens and the encryption keys for stored provider credentials. **If that Mongo data is lost, every session is invalidated and every stored provider credential becomes undecryptable** — there is no recovery without the secret.

`INSTANCE_SECRET` in `apps/api/.env` overrides the stored value unconditionally. Treat it as a break-glass override:

- If you ever plan to manage the secret through the environment, pin `INSTANCE_SECRET` **before** storing any provider credentials — the value must match whatever encrypted them.
- Never set a fresh random value on an instance whose credentials were encrypted under a different secret: that orphans every ciphertext.
- The only copy of an auto-generated secret lives in your MongoDB backups. Keep [backups](#backups) current and protected before any maintenance that could touch the database.

<AccordionGroup>
  <Accordion icon="key" title="Advanced: Manual environment setup">
    `gaia up` writes everything for you, but you can also configure by hand. Create `apps/api/.env`:

    ```bash
    ENV=selfhost
    AUTH_MODE=local
    # Infra — Compose provides these when you use the bundled compose file,
    # but a hand-rolled setup must supply them:
    MONGO_DB=mongodb://mongo:27017/gaia
    REDIS_URL=redis://redis:6379/0
    POSTGRES_URL=postgresql://postgres:postgres@postgres:5432/langgraph
    CHROMADB_HOST=chromadb
    CHROMADB_PORT=8000
    RABBITMQ_URL=amqp://guest:guest@rabbitmq:5672/
    # Machine secrets — generate once, keep stable:
    AGENT_SECRET=$(openssl rand -hex 32)
    BOT_SESSION_TOKEN_SECRET=$(openssl rand -hex 32)
    EMAIL_UNSUBSCRIBE_SECRET=$(openssl rand -hex 32)
    # Optional: pin INSTANCE_SECRET before storing any provider keys (see above)
    # INSTANCE_SECRET=$(openssl rand -hex 32)
    # Optional integrations — leave unset to disable that lane (see Self-Host vs Cloud):
    # OPENROUTER_API_KEY=...
    # R2_ACCOUNT_ID=... R2_BUCKET=... R2_ACCESS_KEY=... R2_SECRET_KEY=...
    # JUICEFS_META_URL_TEMPLATE=postgres://juicefs:pass@postgres:5432/gaia_juicefs_{shard}
    # LIVEKIT_URL=... LIVEKIT_API_KEY=... LIVEKIT_API_SECRET=...
    ```

    Secrets must stay stable across restarts — rotating `INSTANCE_SECRET` or the machine secrets after data exists invalidates sessions and provider keys. See [Environment Variables](/configuration/environment-variables) for the full list.

    Start the stack after writing the file:

## Troubleshooting

<AccordionGroup>
  <Accordion icon="triangle-exclamation" title="Logs show JuiceFSUnavailable">
    The backend can't reach the workspace mount. Check, in order:
    - **Object store and metadata are configured**: `R2_*` and `JUICEFS_META_URL_TEMPLATE` must be set in `apps/api/.env`. Without them JuiceFS never mounts.
    - **FUSE settings are present**, confirm `cap_add: SYS_ADMIN`, `devices: /dev/fuse`, and `security_opt: apparmor:unconfined` are on `gaia-backend` and `arq_worker`.
    - **The mount came up**, run `docker compose -f docker-compose.selfhost.yml exec gaia-backend mountpoint /mnt/jfs`. A non-zero result means the mount failed; check the backend logs for the JuiceFS error.
  </Accordion>
  <Accordion icon="microchip" title="fusermount3: cannot open /dev/fuse">
    The FUSE device isn't reaching the container. Confirm the `devices: /dev/fuse:/dev/fuse` mapping is present. On a Linux host, verify the device exists with `ls -l /dev/fuse` and load the module if missing: `sudo modprobe fuse`. On macOS and Windows, make sure Docker Desktop is running (it provides the device from its Linux VM).
  </Accordion>
  <Accordion icon="lock" title="Mount fails with permission denied">
    The container holds the capability but the host's security profile is blocking the mount. Confirm `security_opt: apparmor:unconfined` is set. On SELinux hosts, you may also need to allow the mount in your local policy.
  </Accordion>
  <Accordion icon="plug" title="Ollama connection test fails">
    The backend reaches Ollama through `http://host.docker.internal:11434`, which the Compose file wires via `extra_hosts: host.docker.internal:host-gateway`. If the test fails: confirm Ollama is running (`curl http://localhost:11434/api/tags` on the host), and on Linux start it with `OLLAMA_HOST=0.0.0.0 ollama serve` so it accepts connections from the Docker gateway.
  </Accordion>
  <Accordion icon="stethoscope" title="Something else is broken">
    Run `gaia doctor` — it walks the stack (Docker daemon, containers, API health, setup status, web reachability, disk headroom) and prints a named fix for each problem it finds.
  </Accordion>
</AccordionGroup>
