The GAIA CLI is the primary way to set up self-hosted GAIA. One command starts the whole stack and hands you off to the browser to finish setup — no hand-editing environment files.

### Installing a beta

Before a release becomes stable, we sometimes publish a beta of it so people can try it early. Betas are numbered like `0.7.0-beta.1`. To install the latest beta, add `GAIA_CHANNEL=beta` to the install command, then run `gaia up` as usual:

```bash
curl -fsSL https://heygaia.io/install.sh | GAIA_CHANNEL=beta sh
gaia up
```

A beta CLI installs the GAIA release built with that beta, so its images and compose files match it. Expect rough edges, and back up first (`gaia backup`) if you put a beta on an install you rely on. When `gaia update` says you are already on a beta's release, it shows the command for the next beta and the command for going back to stable. Go back to stable only once a stable release newer than your beta is out.

## Quick Start

```bash
gaia up
```

The [self-hosting walkthrough](/self-hosting/walkthrough) is the quick start: it runs `gaia up` on a fresh server, lists every flag `gaia up` takes, and finishes setup in the browser. The [CLI reference](/self-hosting/cli-reference) lists every command. The rest of this page explains what `gaia up` does and how to run the install from the terminal afterwards.

## What `gaia up` Does

<Steps>
  <Step title="Prerequisite check">
    Verifies Docker is installed and running. If Docker is missing, the CLI offers to install it for you instead of failing. On Linux, a non-root user is added to the `docker` group and the command relaunches itself under `sg docker`, so there is no need to log out and back in.
  </Step>

  <Step title="Setup files">
    Reuses an existing install if you have one. Otherwise it downloads this release's setup files, `gaia-selfhost-<version>.tar.gz` (the compose files and the Caddyfile), checks them against their `.sha256` and unpacks them into `~/gaia`. Git is not needed.
  </Step>

  <Step title="Environment configuration">
    Writes minimal `.env` files with self-host defaults: `ENV=selfhost` and `AUTH_MODE=local`. The three required machine secrets (`AGENT_SECRET`, `BOT_SESSION_TOKEN_SECRET`, `EMAIL_UNSUBSCRIBE_SECRET`) are generated automatically — you never see or type them. Port conflicts are resolved by picking free ports. Compose settings — the `proxy` profile, the web port, your domain — go to `infra/docker/.env`.
  </Step>

  <Step title="Start the stack">
    Pulls the published multi-arch images (or builds them from source with `--build`, which clones the source on a fresh machine) and starts every service via Compose, behind a single Caddy proxy that serves both the web app and the API on one port.
  </Step>

  <Step title="Hand-off">
    Prints the web URL so you can finish setup in the browser at http://localhost:3000/setup.
  </Step>
</Steps>

## Command Reference

| Command        | What it does                                                        |
| -------------- | ------------------------------------------------------------------- |
| `gaia up`      | One-command start: checks prerequisites, configures, starts         |
| `gaia doctor`  | Diagnoses a broken stack and prints a named fix per problem          |
| `gaia status`  | Services and every dependency (from `/health/ready`), with latency   |
| `gaia update`  | Move to the GAIA release this CLI ships, keeping your data and settings |
| `gaia backup` / `gaia restore` | Back up and restore the databases, volumes and `apps/api/.env` |
| `gaia start`   | Start services                                                       |
| `gaia stop`    | Stop services                                                        |
| `gaia logs`    | Stream logs                                                          |
| `gaia init` / `gaia setup` / `gaia dev` | Contributor commands for a source checkout — see [Developer CLI Commands](/developers/cli-commands) |

## What the Install Holds

The install folder (`~/gaia` by default) holds only what the stack runs and what you own:

- `gaia-selfhost.json`: the list of the release's setup files
- `infra/docker/`: the compose files, `selfhost/Caddyfile` and `selfhost/bot.yml`
- Your own files: `apps/api/.env`, `apps/bots/.env`, `infra/docker/.env` and `backups/`

Run the management commands from inside it. If you work from a source checkout instead, see [Developer CLI Commands](/developers/cli-commands).

## Monitoring Logs

Use `gaia logs` to stream logs for currently running services.

## Diagnosing Problems

When something isn't working, run:

```bash
gaia doctor
```

It walks the whole stack in order — Docker daemon, ports, containers, API health, each backing service from `GET /health/ready` (MongoDB, PostgreSQL, Redis, RabbitMQ, ChromaDB), setup status (plans seeded, provider configured, admin account created), web reachability, disk and memory headroom, and whether you run the release this CLI ships — and prints what's broken with a specific fix for each problem. It exits 1 only when a blocking check fails.

## Updating

```bash
gaia update
```

Moves the install to the GAIA release this CLI version ships. It downloads that release's setup files and checks them, pulls its images (nothing changes if either fails), swaps the new setup files in (removing any the release dropped), pins `GAIA_VERSION` in `infra/docker/.env` and restarts. Volumes and `.env` files are kept. For a newer GAIA, update the CLI first (`curl -fsSL https://heygaia.io/install.sh | sh`), then run `gaia update` again. `--version v<x.y.z>` moves to another release, images and setup files together (only release tags are accepted); `--git` is for contributors running from source.

An install made by an older `gaia up` is a git checkout of a release tag. Its next `gaia update` moves it to the new layout: the tracked files and `.git` are removed, and your settings and backups stay. A checkout on a branch, or one with local edits, is refused and pointed at `gaia update --git`.

## Port Conflict Handling

A self-hosted stack publishes a single port: the proxy's. If it is already in use, the CLI detects the conflict, shows which process is using the port, and suggests an alternative. The API and databases are not published to your machine at all, so they can never conflict.

Port overrides are saved to `infra/docker/.env` inside your GAIA install and persist across restarts. To change them after setup, edit that file directly:

| Variable          | What it controls                                    | Default |
| ----------------- | --------------------------------------------------- | ------- |
| `WEB_HOST_PORT`   | The port GAIA is served on (HTTP)                   | 3000    |
| `HTTPS_HOST_PORT` | The HTTPS port, used with `GAIA_DOMAIN`             | 3443    |
| `GAIA_DOMAIN`     | Domain to serve over HTTPS (set by `--domain`)      | unset   |

<Info>Restart services after editing: `gaia stop && gaia start`</Info>
