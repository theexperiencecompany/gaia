The GAIA CLI is the primary way to set up self-hosted GAIA. One command starts the whole stack and hands you off to the browser to finish setup — no hand-editing environment files.

<Info>
  For installation instructions, see [CLI Installation](/cli/installation). For
  the full command reference, see [CLI Commands](/cli/commands).
</Info>

## Install

<Snippet file="cli-install.mdx" />

Or with the standalone installer (no Node.js needed):

```bash
curl -fsSL https://heygaia.io/install.sh | sh
```

## Quick Start

```bash
gaia up
```

That's the whole setup. When the command finishes it prints `http://localhost:3000` — open it, create your admin account, paste an AI provider key, and start chatting. The browser-side steps are covered in [Self-hosting overview](/self-hosting/overview).

To skip the provider step, hand the key over on the command line. One key is enough, and OpenAI works as well as any:

```bash
gaia up --yes --llm-provider openai --llm-key sk-...
```

Useful flags:

| Flag                 | Effect                                                                                                   |
| -------------------- | -------------------------------------------------------------------------------------------------------- |
| `--yes`              | No prompts at all; also consents to installing Docker on apt-based Linux                                  |
| `--domain <domain>`  | Serve GAIA at `https://<domain>` with an automatic Let's Encrypt certificate (uses ports 80 and 443)        |
| `--web-port <port>`  | Host port GAIA is served on (default 3000)                                                                |
| `--llm-provider <p>` + `--llm-key <key>` | Configure the AI provider at first boot: `openai`, `openrouter` or `gemini` (`custom` is set up in the browser) |
| `--code-sandbox`     | Let the agent run code in local containers through the host Docker socket (root-equivalent; see [Local coding sandbox](/self-hosting/docker-setup#local-coding-sandbox)). Saved, so later starts and updates keep it; `--no-code-sandbox` turns it off |
| `--build`            | Build the images from your checkout instead of pulling them                                              |
| `--no-start`         | Write the configuration without starting services                                                         |

## What `gaia up` Does

<Steps>
  <Step title="Prerequisite check">
    Verifies Docker is installed and running. If Docker is missing, the CLI offers to install it for you instead of failing. On Linux, a non-root user is added to the `docker` group and the command relaunches itself under `sg docker`, so there is no need to log out and back in.
  </Step>

  <Step title="Repository setup">
    Reuses an existing GAIA checkout if you have one; otherwise clones the repository (default: `~/gaia`).
  </Step>

  <Step title="Environment configuration">
    Writes minimal `.env` files with self-host defaults: `ENV=selfhost` and `AUTH_MODE=local`. The three required machine secrets (`AGENT_SECRET`, `BOT_SESSION_TOKEN_SECRET`, `EMAIL_UNSUBSCRIBE_SECRET`) are generated automatically — you never see or type them. Port conflicts are resolved by picking free ports. Compose settings — the `proxy` profile, the web port, your domain — go to `infra/docker/.env`.
  </Step>

  <Step title="Start the stack">
    Pulls the published multi-arch images (or builds them from your checkout with `--build`) and starts every service via Compose, behind a single Caddy proxy that serves both the web app and the API on one port.
  </Step>

  <Step title="Hand-off">
    Prints the web URL so you can finish setup in the browser at http://localhost:3000/setup.
  </Step>
</Steps>

## Command Reference

| Command        | What it does                                                        |
| -------------- | ------------------------------------------------------------------- |
| `gaia up`      | One-command start: checks prerequisites, configures, starts         |
| `gaia doctor`  | Diagnoses a broken stack and prints a named fix per problem          |
| `gaia status`  | Services and every dependency (from `/health/ready`), with latency   |
| `gaia update`  | Move to the GAIA release this CLI ships, keeping your data and settings |
| `gaia backup` / `gaia restore` | Back up and restore the databases, volumes and `apps/api/.env` |
| `gaia start`   | Start services                                                       |
| `gaia stop`    | Stop services                                                        |
| `gaia logs`    | Stream logs                                                          |
| `gaia setup`   | Re-configure an existing GAIA repository                             |
| `gaia dev`     | Run in development mode (for contributors — see [Development setup](/developers/development-setup)) |

## Already Have the Repo?

If you've already cloned GAIA, run the management commands from inside the repository, or reconfigure it directly:

```bash
cd /path/to/gaia
gaia setup
```

This skips cloning and goes straight to environment configuration and project setup.

## Monitoring Logs

Use `gaia logs` to stream logs for currently running services.

In developer mode, `gaia dev` runs in the foreground and shows Nx TUI output in the same terminal. Keep that terminal open, and use another terminal for `gaia logs` when needed.

## Diagnosing Problems

When something isn't working, run:

```bash
gaia doctor
```

It walks the whole stack in order — Docker daemon, ports, containers, API health, each backing service from `GET /health/ready` (MongoDB, PostgreSQL, Redis, RabbitMQ, ChromaDB), setup status (plans seeded, provider configured, admin account created), web reachability, disk and memory headroom, and whether you run the release this CLI ships — and prints what's broken with a specific fix for each problem. It exits 1 only when a blocking check fails.

## Updating

```bash
gaia update
```

Moves the install to the GAIA release this CLI version ships: pulls its images (nothing changes if that fails), checks out the matching compose files, pins `GAIA_VERSION` in `infra/docker/.env` and restarts, then prints what changed. Volumes and `.env` files are kept. For a newer GAIA, update the CLI first (`curl -fsSL https://heygaia.io/install.sh | sh`), then run `gaia update` again. `--version <tag>` pins another release; `--git` is for contributors running from source.

## Port Conflict Handling

A self-hosted stack publishes a single port: the proxy's. If it is already in use, the CLI detects the conflict, shows which process is using the port, and suggests an alternative. The API and databases are not published to your machine at all, so they can never conflict.

Port overrides are saved to `infra/docker/.env` inside your GAIA repo and persist across restarts. To change them after setup, edit that file directly:

| Variable          | What it controls                                    | Default |
| ----------------- | --------------------------------------------------- | ------- |
| `WEB_HOST_PORT`   | The port GAIA is served on (HTTP)                   | 3000    |
| `HTTPS_HOST_PORT` | The HTTPS port, used with `GAIA_DOMAIN`             | 3443    |
| `GAIA_DOMAIN`     | Domain to serve over HTTPS (set by `--domain`)      | unset   |

<Info>Restart services after editing: `gaia stop && gaia start`</Info>
