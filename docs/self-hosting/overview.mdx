Run GAIA entirely on your own machine. Install the CLI, run `gaia up`, and finish setup in your browser: create an admin account, paste an API key for any supported AI provider (or point GAIA at a local Ollama), and start chatting. No cloud accounts, no secret managers, no hand-edited environment files.

## What runs

Everything runs as Docker containers managed by Compose:

| Component          | What it is                                                        |
| ------------------ | ----------------------------------------------------------------- |
| Proxy              | Caddy — the single entrypoint, http://localhost:3000               |
| Web                | Next.js app, served by the proxy at `/`                            |
| Backend            | FastAPI plus a background worker, served by the proxy at `/api/v1` |
| Databases/Infra    | PostgreSQL, MongoDB, Redis, ChromaDB, RabbitMQ                     |
| File storage       | Local Docker volumes for uploads and each user's workspace (artifacts, installed skills) |

Only the proxy publishes a port on your machine; the API and databases stay on the internal Docker network. Because the browser talks to a single origin, GAIA works on any hostname or IP with no URL configuration.

All state lives in Docker volumes, so stopping containers or upgrading later keeps your chats, accounts, and settings intact.

## Prerequisites

- **Docker**. If it's not installed, `gaia up` detects that and offers to install it for you.
- 2+ CPU cores, **8 GB RAM**, 10 GB+ disk. The stack boots in less, but the local embedding model loads about 1.8 GB into both the API and the worker the first time memory is used, so smaller machines run out of memory then, not at boot
- One AI provider to power chat: an API key from OpenAI, OpenRouter or Google Gemini, any OpenAI-compatible gateway (OpenCode, Nous Research, …) — or [Ollama](https://ollama.com) running locally, which needs no key at all

## Quick start

<Steps>
  <Step title="Install the GAIA CLI">
    <CodeGroup>

    ```bash curl
    curl -fsSL https://heygaia.io/install.sh | sh
    ```

    ```bash npm
    npm install -g @heygaia/cli
    ```

    </CodeGroup>
  </Step>

  <Step title="Start GAIA">
    ```bash
    gaia up
    ```

    One command, zero prompts on a normal machine. It checks prerequisites (offering to install Docker if it's missing), clones GAIA if you don't have it yet, picks free ports, generates the required machine secrets automatically, pulls the published images, and starts every service. When it finishes it prints the URL — open it in your browser.

    On a server, `gaia up --yes` runs with no prompts at all, including installing Docker on apt-based Linux. Add `--llm-provider openai --llm-key sk-...` to configure the AI provider in the same command. To serve GAIA over HTTPS on your own domain, add `--domain gaia.example.com` — see [HTTPS on your own domain](/self-hosting/docker-setup#https-on-your-own-domain).

    No terminal? See [One-click deploy](/self-hosting/one-click-deploy) for cloud-init, Render, DigitalOcean and Dokploy.
  </Step>

  <Step title="Create your admin account">
    Open http://localhost:3000/setup and sign up with your email and a password. The first account created becomes the instance admin. After that, sign-up is invite-only: in **Settings → Members** you create invite links for the people you want to add, or switch on open sign-up. Every member gets their own chats, tasks and connected apps; the AI provider keys are shared, and only the admin can change them.
  </Step>

  <Step title="Pick an AI provider">
    Choose one provider and paste its API key — that's the whole configuration. Base URLs and default models are prefilled where they apply, and a live connection test verifies the key before saving.

    | Provider       | What you provide                                                                                       |
    | -------------- | ------------------------------------------------------------------------------------------------------ |
    | OpenAI         | API key                                                                                                |
    | OpenRouter     | API key                                                                                                |
    | Google Gemini  | API key                                                                                                |
    | Ollama         | Nothing to paste — the base URL is prefilled to `http://host.docker.internal:11434` and the model list is fetched live from your local Ollama |
    | Custom gateway | Any OpenAI-compatible endpoint; presets prefill OpenCode and Nous Research                             |

    You can also skip this step and add a provider later — chat just stays quiet until one is configured.
  </Step>

  <Step title="(Optional) search and connections">
    Add a Tavily API key to give GAIA web search, and connect apps like Gmail or GitHub through your own Composio project ([guide](/self-hosting/composio-integrations)). Both are optional and can be skipped.
  </Step>
</Steps>

That's it — you land in chat.

## Changing things later

Everything the setup wizard asks can be changed afterwards in **Settings → AI Providers**: add, replace, or remove providers any time. Changes apply immediately — no restart needed. Keys are stored encrypted and validated with a live test before saving.

App integrations like Gmail, Calendar and GitHub connect through your own Composio project. Set them up in **Settings → Integrations setup**; see [Connect integrations](/self-hosting/composio-integrations).

## How self-hosting differs

Self-hosted instances run the same code as GAIA Cloud, with a configuration profile designed to need almost nothing from you:

- **Minimal required configuration.** The instance runs with `ENV=selfhost`. The only required values are database URLs (which Compose provides) and three machine secrets — `AGENT_SECRET`, `BOT_SESSION_TOKEN_SECRET`, and `EMAIL_UNSUBSCRIBE_SECRET` — which `gaia up` generates for you.
- **Local accounts, not WorkOS.** Self-host sets `AUTH_MODE=local`, which enables email-and-password sign-in. Hosted and development deployments use `AUTH_MODE=workos`; see [Environment variables](/configuration/environment-variables).
- **One generated instance secret.** `INSTANCE_SECRET` signs sessions and encrypts the provider keys you save in Settings. `gaia up` generates it into `.env` on a fresh install, so the key lives apart from the database. Without it, the instance generates one on first boot and keeps it in the database alongside the encrypted keys, which means a database dump alone is enough to read them.
- **No Infisical.** Self-host resolves all configuration locally and never contacts Infisical, even if leftover credentials exist in the environment.
- **Unlimited usage.** Usage is tracked locally for insights, but plan limits are never enforced.
- **No payments, no plans.** There is no billing integration in self-host mode: every user gets every feature, and billing UI is hidden.
- **Opt-in code execution.** The coding tools need either an E2B key or the local sandbox (`gaia up --code-sandbox`), which gives the containers root-equivalent access to the host. See [Local coding sandbox](/self-hosting/docker-setup#local-coding-sandbox).
- **Files stay on your server.** Uploads, generated images and each user's workspace live on local Docker volumes, with no Cloudinary or object-storage account. See [File storage](/self-hosting/docker-setup#file-storage).

## Using Ollama

The backend runs inside a container, so `localhost` inside the container is not your machine. The Compose stack maps `host.docker.internal` to the host gateway (`extra_hosts: host.docker.internal:host-gateway`), and the setup wizard prefills the Ollama base URL accordingly. If Ollama is running, just accept the prefill and pick a model from the live list.

<Tip>
  On Linux hosts, Ollama listens on `127.0.0.1` by default, which the container cannot reach. Start it with `OLLAMA_HOST=0.0.0.0 ollama serve` so it accepts connections through the gateway.
</Tip>

## Keeping GAIA up to date

```bash
gaia update
```

Each CLI release ships one tested GAIA release. `gaia update` pulls that release's images, checks out its compose files, pins `GAIA_VERSION` in `infra/docker/.env`, restarts, and prints what changed. If the pull fails, nothing about the install changes. For a newer GAIA, update the CLI first (`curl -fsSL https://heygaia.io/install.sh | sh`), then run `gaia update`.

Data lives in Docker volumes and the database, so updating never touches your chats or settings.

## When something breaks

```bash
gaia doctor
```

It walks the whole stack — Docker daemon, containers, API health, every database and queue (from the API's `GET /health/ready`), web reachability, configured providers, memory and disk — and prints what's broken with a specific fix for each problem. `gaia status` shows the same per-dependency view at a glance. See [CLI setup](/self-hosting/cli-setup) for everything the CLI can do.

## Backups

```bash
gaia backup                  # dumps MongoDB + PostgreSQL to ./backups/
gaia restore --from backups  # restores the latest dumps
```

MongoDB holds your accounts, chats and the encrypted provider keys; PostgreSQL holds agent state. See [Backups](/self-hosting/docker-setup#backups) for details.
