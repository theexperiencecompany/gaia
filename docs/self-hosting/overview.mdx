Run GAIA entirely on your own machine. Install the CLI, run `gaia up`, and finish setup in your browser: create an admin account, paste an API key for any supported AI provider (or point GAIA at a local Ollama), and start chatting. No cloud accounts, no secret managers, no hand-edited environment files.

## What runs

Everything runs as Docker containers managed by Compose:

| Component          | What it is                                                        |
| ------------------ | ----------------------------------------------------------------- |
| Proxy              | Caddy — the single entrypoint, http://localhost:3000               |
| Web                | Next.js app, served by the proxy at `/`                            |
| Backend            | FastAPI plus a background worker, served by the proxy at `/api/v1` |
| Databases/Infra    | PostgreSQL, MongoDB, Redis, ChromaDB, RabbitMQ                     |
| File storage       | Local Docker volumes for uploads and each user's workspace (artifacts, installed skills) |

Only the proxy publishes a port on your machine; the API and databases stay on the internal Docker network. Because the browser talks to a single origin, GAIA works on any hostname or IP with no URL configuration.

All state lives in Docker volumes, so stopping containers or upgrading later keeps your chats, accounts, and settings intact.

## Prerequisites

- **Docker**. If it's not installed, `gaia up` detects that and offers to install it for you. Git is not needed.
- 2+ CPU cores, **8 GB RAM**, 10 GB+ disk. The stack boots in less, but the local embedding model loads about 1.8 GB into both the API and the worker the first time memory is used, so smaller machines run out of memory then, not at boot
- One AI provider to power chat: an API key from OpenAI, OpenRouter or Google Gemini, any OpenAI-compatible gateway (OpenCode, Nous Research, …) — or [Ollama](https://ollama.com) running locally, which needs no key at all

## Self-host vs Cloud

Self-hosted GAIA runs the same code as GAIA Cloud, with a profile that needs almost nothing from you. It runs with `ENV=selfhost` and `AUTH_MODE=local`; Cloud and development use `AUTH_MODE=workos`.

| Area | Cloud (heygaia.io) | Self-host |
| --- | --- | --- |
| **Sign-in** | WorkOS: Google sign-in, hosted sessions | Email and password. The first account is the admin; others join by invite link (**Settings → Members**) |
| **Billing** | Plans and limits | None. Every user gets every feature; usage is tracked locally for insights only |
| **In-app support** | Requests go to GAIA's support team | Nothing is sent to GAIA. The support form links to [GitHub issues](https://github.com/theexperiencecompany/gaia/issues) and [discussions](https://github.com/theexperiencecompany/gaia/discussions) |
| **Configuration** | Every service key, from Infisical | Only the database addresses (Compose provides them) and three machine secrets, `AGENT_SECRET`, `BOT_SESSION_TOKEN_SECRET` and `EMAIL_UNSUBSCRIBE_SECRET`, which `gaia up` generates. Never contacts Infisical, even if old credentials are in the environment |
| **Instance secret** | Managed | `INSTANCE_SECRET` signs sessions and encrypts the keys you save. `gaia up` writes it to `.env` on a fresh install, so the key lives apart from the database. Without it, GAIA generates one on first boot and keeps it in the database next to the keys, so a database dump alone can read them |
| **AI and tools** | Managed keys | Bring your own, in **Settings → Providers & Tools**. See [AI models and tools](/self-hosting/ai-models-and-tools) |
| **Files** | Cloudinary and R2 | Docker volumes on your server. See [File storage](/self-hosting/ai-models-and-tools#file-storage) |
| **Running code** | E2B | Off until you add an E2B key or turn on the local sandbox. See [Running code](/self-hosting/ai-models-and-tools#running-code) |
| **Voice and browser automation** | Available | Not available. See [Not available on self-host](/self-hosting/ai-models-and-tools#not-available-on-self-host) |
| **Logs** | Loki and Grafana | Container logs only, 10 MB × 3 rotated files per service |
| **Updates and backups** | Managed | `gaia update`, `gaia backup` and `gaia restore`. You own the dumps |

## Keeping GAIA up to date

```bash
gaia update
```

Each CLI release ships one tested GAIA release. `gaia update` downloads and checks that release's setup files, pulls its images, swaps the setup files in, pins `GAIA_VERSION` in `infra/docker/.env`, restarts, and prints what changed. If the download or the pull fails, nothing about the install changes. Your `.env` files and data stay. For a newer GAIA, update the CLI first (`curl -fsSL https://heygaia.io/install.sh | sh`), then run `gaia update`.

Data lives in Docker volumes and the database, so updating never touches your chats or settings.

## When something breaks

```bash
gaia doctor
```

It walks the whole stack — Docker daemon, containers, API health, every database and queue (from the API's `GET /health/ready`), web reachability, configured providers, memory and disk — and prints what's broken with a specific fix for each problem. `gaia status` shows the same per-dependency view at a glance. See [CLI setup](/self-hosting/cli-setup) for everything the CLI can do.

## Backups

```bash
gaia backup                  # dumps MongoDB + PostgreSQL to ./backups/
gaia restore --from backups  # restores the latest dumps
```

MongoDB holds your accounts, chats and the encrypted provider keys; PostgreSQL holds agent state. See [Backups](/self-hosting/maintenance#backups) for details.
